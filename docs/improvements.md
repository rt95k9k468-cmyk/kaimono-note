### A1 日記の保存場所

- **いま**：日記の本文は `state.archive.days[].memo`。買うもの・やること・からだと
  同じ localStorage の一本（`kaimono-note-v2`）に、**平文で**入っている（書くのは
  `screen-archive.js` の `openLogSheet` → `store.setDayLog`、975行）。
- `js/diary.js`（IndexedDB `kaimono-diary` と AES-GCM の暗号）は、index.html・sw.js・
  build-standalone.js に登録されて読み込まれているが、**どこからも呼ばれていない**
  （`KN.diary.` の呼び出しはゼロ）。冒頭のコメント「だから本文は state に入れません」
  は、いまの実際と食い違っている。
- `tools/diary-import.html` が作る `kurashi-diary-◯days.json`（`kind: "diary-sealed"`）を
  アプリへ入れる口も無い（`importSealed` を呼ぶ画面が無い）。
- **起こりうること**：
  - 容量。diary.js 冒頭の実測で「2151日×600字＝4.1MB」、iOS の localStorage は
    原点あたり約5MB。**live と自動控え（上限 150万字、ただし最低一世代）が同じ枠を
    分け合う。** 日記が伸びると、先に控えの世代が減り（A2-3）、やがて live の保存
    そのものが「保存できませんでした」になる。
  - 手が止まるたび（500ms）に state 全体を書き直す。量に比例して重くなる。
  - 平文なので、端末の中・書き出したファイル・自動控えのどれからも読める。
- **直し方の案**：
  - (a) 置き場所はそのまま、容量を見張る。設定に使用量（live・控え）を出す。live の
    保存が容量で落ちたら、控えの細かいほうを間引いて一度だけ書き直す（A2-4 と同じ直し）。
  - (b) 本文を IndexedDB へ移す（diary.js を使う）。暗号にするかは利用者が決める
    （鍵を失うと二度と戻らない）。書き出し・自動控え・復元の**三つ全部**に日記を
    足すこと（足さないと、そのまま A4 の漏れになる）。
- **移行**：(a) は無し。(b) は**要る**（`archive.days[].memo` を IndexedDB へ写す）。
  やるなら「写す → 読み比べて一致を確かめる → 元は消さずに残す」の順で、実行前に報告。
- **状態**：利用者の判断待ち（(a) か (b) か。(b) なら暗号の有無）。

### A2 自動控え

- **いま**：`backup.js`。離れるたび（`visibilitychange` / `pagehide`）と一時間おきに、
  state まるごとを `kaimono-note-snapshots` に積む。
- **起こりうること**：
  1. **daily を数えていない。** `isEmpty()`（153–159行）は買うもの・やること・
     ダイエットしか見ない。daily しか無い state は「空」とされ、控えを取らない。
     「削除前」「復元前」「サンプル読込前」も同じで、呼び出し側（screen-settings.js
     2226・2306・2321行、backup.js 204行）は戻り値を見ていない——確認の文は
     「直前の状態は自動バックアップに残る」と言うのに、残らない。urges を足したときに
     塞いだのと同じ種類の穴（docs/health.md「それしか書いていない人の控えが『空』」）。
  2. **一覧の説明が買い物の数だけ。** `summarize()`（134–140行）は商品・店舗・リスト
     だけ。設定の「自動バックアップ」（screen-settings.js 1269行）で、日記やダイエットの
     変化がどの控えに入っているか見分けられない。
  3. **大きくなると、世代が黙って減る。** `prune()` の上限（`BUDGET` 150万字、
     106–114行）は**細かいほう（直近2日の一時間おき）から**落とす。state が十数万字を
     超えるあたりから、直近2日ぶんは「いちばん新しい一つ」しか残らない。「さっき
     消してしまった」を、離れる前の控えが上書きして戻せなくなる。復元の「戻す前の
     控え」も、次に書いて離れたときに押し出されうる。
  4. **live の保存が落ちても、控えは退かない。** `write()`（118–132行）は控え自身の
     失敗しか見ない。`store.persist()`（store.js 1031–1037行）は容量で落ちても控えを
     間引かない。
  5. 控えの時刻は UTC（`today()`）で、日に一つの区切り（`dayOf`、66・95行）も UTC。
     日本時間では**朝9時**で日が替わる。
- **直し方の案**：`isEmpty` と `summarize` に daily（entries・中身のある days）を
  足す。安全のための控え（削除前・復元前）が取れなかったら、進む前に知らせる。世代が
  減っていることを設定に出す。live の保存が落ちたら控えを間引いて一度だけ書き直す。
  日の区切りを `dayKey()` 系に揃える。
- **移行**：無し。既存の控えは消さない（古い控えの `summary` に無い項目は「—」と出す）。
  ただし**区切りや上限を変えると、次に書くときの prune で既存の控えの残り方が変わる**
  ——そこは変える前に報告。
- **状態**：利用者の確認待ち（backup.js に触れるため）。

### A3 バックアップの保存確認

- **いま**：`screen-settings.js` の `saveBackup()`（2192–2207行）。`<a download>` を
  押した**直後に** `markExported()`（前回の書き出し日時を「いま」にする）と
  「バックアップを保存しました」。
- **起こりうること**：iPhone で保存の画面を取り消しても、失敗しても、アプリには
  分からず、設定には「前回 9/26」と出る。1秒後に `revokeObjectURL`（2203行）して
  いるので、保存の確認に1秒以上かかると中身を取りに行けずに失敗する**おそれがある**
  （実機で要確認）。設定の説明（`exportSub`、1036–1041行）は「◯商品・◯店舗を
  JSONで書き出します」で、やること・daily・ダイエットも入っていることが伝わらない。
  なお `exportDue()` はどこからも呼ばれていない。
- **直し方の案**：
  1. 使える端末では共有シート（`navigator.share({ files })`）で渡し、**終わったとき
     だけ**記録する（取り消しは記録しない）。使えない端末は、いまの方法のあとに
     「保存できましたか？」と一度だけ訊く。
  2. 「控えを確かめる」を足す。保存したファイルを選ぶと、**復元はせずに**中を読み、
     書き出した日時・件数・いまとの差を見せる。
  3. revoke を遅らせる。
- **移行**：無し（確かめた日時を持つなら settings に欄を足し、`reconcile()` で既定へ）。
- **状態**：利用者の確認待ち（確かめ方をどれにするか）。

### A4 復元の漏れ

- **いま**：`store.importJSON()`（store.js 3291–3311行）が、戻す欄を一つずつ列挙する。
- **起こりうること**：
  1. **列挙から漏れている欄**：`iconOverrides`（食事メモの絵の言い換え）と
     `iconReports`。書き出しにも自動控えにも入っているのに、戻すときに入らない。
     機種変更で失われる。自動控えから戻しても、この二つだけはいまのまま残る。
     3307–3308行のコメントが警告しているのと同じ種類。
  2. **違うファイルを選ぶと、全部が空に置き換わる。** `schema >= 2` でないものは
     `migrateV1()`（941行〜）へ回るが、これは `products` と `listItems` しか読まない。
     daily の月の書き出し（`daily-2026-09.json`、`kind: "daily-month"`）や、日記の
     取り込み道具の出力（`kind: "diary-sealed"`）を選ぶと、**空の state で全部を
     置き換え**、しかも「復元しました」と出る。どちらも .json なので選べてしまう
     （screen-settings.js 2213行）。頼みは「復元前」の控えだけで、それも A2-1 では
     取られず、A2-3 では押し出されうる。
  3. 将来 A1(b) で日記を IndexedDB に移すなら、書き出し・控え・復元に日記を足さないと、
     そのまま漏れになる。
- **直し方の案**：置き換える前に中身を確かめる（`app === "kaimono-note"` か、`schema`
  があるか。`kind` が daily-month / diary-sealed なら「これはバックアップでは
  ありません」で止める）。置き換える前に「このファイル：◯月◯日の書き出し・
  買うもの◯・やること◯・daily◯日…」を見せる。`iconOverrides` と `iconReports` を
  戻す欄に足す（足し忘れそのものを防ぐなら、`reconcile()` の結果を丸ごと取り、
  置き換えない欄だけを名指しする形にする）。
- **移行**：無し。
- **状態**：利用者の確認待ち（復元処理に触れるため）。

### A5 日付の埋め方（題名からの読み。どちらか要確認）

**候補1（本命）：日記の本文の頭に書き込む日付。** `screen-archive.js` の
`dailyStamp()`（916–927行）が、空の日を開いたときに「2026.09.26（土）」と
「育休完了まであと◯日」を**本文そのものに**下書きする（`memoInit`、933行）。

- 起こりうること：起きた・寝た時刻だけを入れても、本文・起床・就寝をまとめて比べて
  いる（969–977行）ので保存が走り、**下書きの日付だけの本文**が残る。自分で書いた
  本文と見分けがつかない。日付は行の見出しにも出るので二重になる。日付を本文に
  **写す**ので、「写さず引く」とは逆向き。「あと◯日」は両端を含めて数える（924行の
  `+1`）ので、終了予定日の前日に「あと2日」、当日に「あと1日」と出る——意図どおりか
  要確認。
- 直し方の案：下書きは「本文に一字でも触れたときだけ」保存する。または日付と残り日数を
  本文には入れず、**見出しとして出すだけ**にする（新しい日から）。
- 移行：新しい日からなら無し。**既存の本文から日付の行を外すのは作り替え**なので、
  やらない（やるなら先に報告）。

**候補2：読み込み時の埋め合わせ。** `store.js` の `reconcile()`（662–689行）。

- 日付の無い積み上げは `todayKey()` で**読み込んだ日**に付け替わり（667行）、次の保存で
  固まる。形式の検査も無い（「2026/9/5」はそのまま通り、どの日にも出ない）。時刻付きの
  UTC の値なら先頭10文字で切るので、日本時間の0〜9時のものが前の日になる（`dayKeyOf`、
  2911行も同じ形。いまの呼び出し元は、見た範囲では全部ローカルの日のかぎを渡して
  いるので、実際には起きていない）。
- 作成・更新時刻の無いものは日付だけで埋める（668–669・687–688行）。表示の
  `formatStamp` は日付だけの値を正しく扱うので、日本時間では問題にならない。
- 直し方の案：日付の無いものは `createdAt` のローカルの日から取り、それも無ければ
  付け替えない。時刻付きの値は `dayOfStamp()`（1600行）と同じくローカルの日に直す。
- 移行：いま正しい記録は動かない形にする。過去に「読んだ日」へ付け替わったものは、
  見分けがつかないので戻せない。
