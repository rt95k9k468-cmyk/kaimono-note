# 絵の引き当て（findKey・hasWord・icon-eval・絵の報告）

CLAUDE.md から見出しごと移した、詳しい決めごと（2026年9月26日）。
本文は移す前と一字も変えていない。入口（どの docs を読むか）と、どの画面でも
踏む罠は CLAUDE.md にある。**新しい決めごとは、ここ（該当する docs）に書く。**

### かな2文字の言葉は、短い名前のときだけ当てる

`product-icons.js` の `findKey` / `icons-todo.js` の `findKey` の共通の決めごと。
かな2文字（「ぱす」等）は品物の名を成さないので、**名前が4文字までのときだけ**
当てる（品物の名は短く、用事の文は長いので、その差で切る）。漢字は2文字でも
名を成す（洗剤・牛乳）ので、そのまま当てる。かな2文字の言葉自体は残す
（「あめ」「のり」「ねぎ」等74個。「焼きのり」「長ねぎ」に当たらなくなる
ほうが失うものが大きい）。実例は `ICON-TODO.md`。

### カタカナの連なりは、後ろが主役（`KN.util.hasWord`）

`findKey` は長いあいだ「文字列に含まれるか」だけを見ていた。ひらがな・漢字の
混ざる文はそこで語の切れ目が見えるが、**カタカナ（とラテン字）を続けて書いた
ところは切れ目が見えない**——「タコス」の中に「たこ」が、「ペットボトル」の中に
「ぺっと」が、「オレンジジュース」の中に「おれんじ」が居る。実測で、蛸・犬猫・
みかんの絵がそれぞれ出ていた。

判定は `KN.util.foldRuns` ／ `KN.util.hasWord` の**一組だけ**（買うものの辞書と
「こと」の辞書が分け合う。二か所に書くと片方だけ直した日に割れる）。`foldRuns`
は `foldKana` と同じ文字列に、**同じ長さの字の種類の並び**を添えて返す
——カタカナ→ひらがなの置き換えは一字が一字なので位置がずれず、折りたたむ前の
種類を折りたたんだあとの位置で読める。

決めごとは四行：

- 連なりの**終わりまで届く**当たりは採る。日本語のカタカナ語は後ろが主役
  （オレンジ**ジュース**はジュース、ポテト**サラダ**はサラダ、ミニ**トマト**は
  トマト）。
- 途中で切れている当たりは、**残りの後ろが辞書の言葉なら譲る**
  （オレンジ｜ジュース、チーズ｜ケーキ、レトルト｜カレー）。ただし
  **譲る相手には丈が要る**（`TAIL_SLACK`、下記）。
- 後ろが辞書に無いときだけ前半を採る。ただし連なりの**頭から**始まっている
  なら4字以上（`HEAD_MIN`。「コーヒー｜フィルター」は珈琲でよいが、「タコ｜ス」の
  たこは連なりの中でたまたま揃っただけ）。
- **途中から**始まっている当たりも、**5字以上**なら採る（`MID_MIN`）。頭に
  固定していたので、「一本満足**バー｜プロテイン｜ブラック**」の ぷろていん が
  落ちて、ぶ｜**らっく** が棚として出ていた。4字にすると「ノンア｜ルコール」の
  あるこーる が消毒液として立つので、ここだけ一段高い。

**位置を返す口は `KN.util.wordAt`。`hasWord` はその薄い衣。** 同じ語が二度出る文
では最初の当たりが落ちて二つめが採られることがあり、`indexOf` で取り直すと
**落ちたほうの場所**を見る。括弧の内外を見る側（下記）にはそれが効くので、
判定した本人に場所を言わせる。**判定は一か所だけ。**

#### 譲る相手には、丈が要る（`TAIL_SLACK`）

「譲る」を無条件にしていたころ、**7文字の頭が3文字の後ろに席を譲っていた**
——「カップヌードル｜チリトマト」がトマトに、「バープロテイン｜ブラック」が
棚になっていた。後ろが主役なのは**後ろが主名詞のとき**の話で、商品名のうしろに
味や色の名前が続く書き方はそうではない。

**ここは構造では分けられない。** 実測で確かめたこと：

| 同じ形（長い頭 ＋ 3文字の後ろ） | 正解 |
|---|---|
| カップヌードル(7) ｜ チリ**トマト**(3) | **頭**（cupNoodle） |
| ノンあるこーる(5) ｜ **ビール**(3) | **後ろ**（beer） |
| カマンベール(6) ｜ **チーズ**(3) | **頭**（camembert） |
| レトルト(4) ｜ **カレー**(3) | **後ろ**（curry） |

分かれ目は語そのものの性質——**修飾語か品物の名前か**——で、それは文字列の形の
どこにも書いていない。だから `hasWord` が引けるのは**丈だけ**：1字ぶんの遊び
（`TAIL_SLACK = 1`）を置いて、**後ろが自分より2字以上短ければ譲らない**。
実測で `とまと`(3) は `かっぷぬーどる`(7) に譲らず、`どりんく`(4) は
`よーぐると`(5) に譲る（ヨーグルトドリンクは飲み物のまま）。
残りは `product-icons.js` の `MODIFIER` が名指しで持つ。

#### 一つに絞る順位は四段（`findKey`）

`findKey` は**当たったものをその場で返さない**。`FLAT` は長さの降順なので
「いちばん長い当たり」が先に来るが、長さだけでは決まらないものが二つある。
**候補を集めてから順位で選ぶ**：

1. **括弧の外 ＞ 括弧の中**（`depthsOf`）。食事メモの
   「食パン8枚切り2枚**(チーズとポテサラとジャム)**」は、括弧の中が付け合わせの
   注記で、主役ではない。以前はここで `ちーず` が勝っていた。
2. **修飾語でない ＞ 修飾語**（`MODIFIER`）。れとると・あるこーる・冷凍・冷蔵・
   業務用。どれも中身の語より**長い**ので、長さだけだと包装や形態の絵が勝つ。
   **単独で書かれたときは競争相手がいない**ので、「レトルト」「アルコール」は
   これまでどおりその絵が出る。
3. **長いほう**（これまでと同じ）。
4. **辞書に書いた順**（これまでと同じ）。

**同点の決着を「文中で先」に代えるのは、試して外した。** 日本語の複合語は
**後ろが主名詞**なので、実測で「さば水煮**缶**」が水になる（缶と水がどちらも
1文字で同点、水のほうが先に出てくる）。先頭が主役なのは**列挙**のときだけで、
列挙かどうかは括弧と読点が言う——だから見るのは位置ではなく**括弧**。

**食事メモを「と」や括弧で割る案も、外した。** 当時 `screen-diet.js` の
`slotMarks` が行・読点で割って絵を最大5つ並べていて、そこをさらに割ると
**1行から複数の絵**が出る。**1行＝絵は一つ**にそろえる決めごとなので、
括弧は「割る」のではなく「**減点する**」（上の一段目）。なお「と」割りの
危険は実測で小さかった（生の表記339件のうち割れるのは「とんかつ」「とり天」の
2件、どちらも語頭）——外した理由は危険ではなく、**1行1つ**の決めごとのほう。
（**食事メモの絵そのものは、その後なくなった**。ただし括弧の減点は
`findKey` の順位付けとして生きているので、この決めごとは残る。）

`suggest()`（もしかして、の一覧）は**これまでどおり広く拾う**——選ぶのは人なので、
候補は多いほうがよい。狭めるのは、黙って決めてしまう `findKey` のほうだけ。

### 当たり外れは `icon-eval.json` で数える

入力と、そこから出てほしい絵の名前の表。`want` が**空の配列なら「何も出さないのが
正解」**（間違った絵より、絵が無いほうがよい——これがこの表のいちばん大事な列）。
`gap: true` は「その絵は要るのに語彙が無い」もので、取りこぼしとして別に数える。
`screen` が引き方を決める（やること＝こと辞書→品物辞書、食事＝量を落としてから
品物辞書、買うもの＝品物辞書）。走らせる道具はテストと同じ扱いでスクラッチに置き、
コミットしない。

実測（2026年9月11日、155件）：**誤爆 10件(6.5%) → 3件(1.9%)、命中 92.3% →
95.5%**。残る3件はどれも語彙側の話（「不用品」がゴミ箱・「わっくす」が整髪料・
「まかろにさらだ」がポテトサラダ）で、引き方では直せない。

**段階C（2026年9月11日）で、この3件と gap:true の4件（タイヤ交換／タコスを
作る／ペットボトル／カレーパン）を片づけた——命中 **100%（155/155）**。**
- 「不用品」「まかろにさらだ」は、ユーザー確認のうえ**現状維持**と決め、
  `want` をいまの引き当たりに合わせた（ゴミ箱／ポテトサラダのままでよい）。
- 「わっくす」だけは除外を足した。`findKey` に `AVOID` という小さな表を
  設け、「わっくすがけ」「わっくすをかける」の形だけ hairWax を除外する
  （`js/product-icons.js`）。ひらがなの言葉は `hasWord` のカタカナ連なり
  判定が効かない（`cls` が 0 なので即マッチ）ので、Stage Aの仕組みでは
  この形の誤爆を直せなかった。
- 4件の gap は、それぞれ足りない語を一語足しただけ（`たいや交換`→
  carFront、`たこすを作`→cooking、`ぺっとぼとる`→water、`かれーぱん`→
  sweetBun）。

**引き方の作り直し（2026年9月11日）で 202件に増えた——命中 100%（202/202）。**
食事メモのように**複数の食べ物が1行に同居する入力**を、この表は一件も持って
いなかった（1行1品ばかりだったので、カレーライスが米になっても 99.5% 通った）。
足したのは報告された4件と、**直してはいけない対**のほう
——レトルトカレー・ノンアルコールビール・さば水煮缶・オレンジジュース・
ヨーグルトドリンク。あれは「カップヌードル｜チリトマト」と同じ形で答えが逆なので、
網に載せておかないと、次に順位を触った人が黙って壊す。

**回帰は、この表だけでは足りない。** 引き方を触ったら、**辞書の全キーワード**で
新旧を突き合わせること（品物2131語＋こと684語＋食品データ177件＋この表＝実測
5892通りの引き当て）。キーワードは `KN.util.hasWord` / `wordAt` を黙らせて
`findKey` を一度走らせれば、走査した語がぜんぶ手に入る。今回の作り直しで
変わったのは**9件だけ**で、全部が意図した改善だった——この数が二桁になったら、
どこかで別のものを壊している。

**この表を回す道具（node harness）は `js/icon-system.js` → `js/icons-v2.js`
→ `js/util.js` → `js/product-icons.js` → `js/icons-todo.js` →
`js/food-data.js` の順で読み込むこと。** `icons-v2.js` を抜かすと
`KN.iconsV2Keys`（`product-icons.js` が `KEYS.push(...KN.iconsV2Keys)` で
取り込む旧語彙——mail・movie・trashOut・seaweedWakame 等）が無いまま動くので、
実際のブラウザでは当たる4件が道具の中だけ外れて見える（段階Cでこれにハマった）。

### 自分だけの言い換えと、絵の報告（`iconOverrides` / `iconReports`）

買うもの・やることは記録そのものが `icon` 欄を持てる（`product.icon` /
`t.icon`）ので、絵を選ぶ紙は**一覧の行の丸を押した瞬間に直接開きます**
——買うものは `screen-list.js` の `.item-emoji.js-emoji`、やることは
`screen-todo.js` の `todoRow()` に置いた `.todo-mark-btn.js-icon-pick`。
品目の紙・詳細の紙の中の絵からも同じ紙が開きます（道が二つあるだけです）。

- **時間割の丸薬（`.tl-node`）は、この道に入れません。** あそこは時刻を
  持っている絵で、押せば詳細の紙が開く、が意味です。揃えるのは「一覧」
  どうしだけ——`itemRow` を使う行（時間割・長期タスク）は据え置き。
- タイルでは丸も題も一つのボタンの中なので、これまでどおり押せば紙が
  開きます（丸だけを的にする余地が無いため）。買うものと同じ線引きです。

**`state.iconOverrides` は、いま読む側だけが生きています。**
入力した文字列そのものを鍵にした辞書（畳むのは `KN.util.foldKana`）で、
`product-icons.js` の `findKey` が辞書を引くより先にここへ聞きます
（`store.js` は `product-icons.js` より後に読み込まれるので、モジュール
評価時ではなく**呼び出された瞬間**に `KN.store` を読みます——`byKey` が
`iconsGoods`/`iconsFood` を呼び出し時に読むのと同じ理由。node の harness
は store.js を読み込まないので、`KN.store` が無ければ素通りします）。

- **書く側（`store.setIconOverride`）には、呼び出し元がもうありません。**
  唯一の入口だった食事メモの絵（`slotMarks` / `openMealIconPicker`）を
  外したためです。**消さずに残してあります**——保存済みの上書きは
  `findKey` がいまも読むので、**消すと利用者の選んだ絵が黙って外れます**。
- 買うもの・やることにも同じ経路が効きますが、実害はありません。そちらは
  `product.icon`/`t.icon` のほうが `findKey` より手前で読まれるので、
  すでに絵が決まっている記録はここまで来ません。

#### 困りごとは二種類。分けて溜める（`iconReports`）

**絵が合わないと言っても、中身が二つあります。**

- **言葉が無い**（`kind: "missing"`）… 辞書がその言葉を一つも引けない。
  → 辞書に言葉を足せば直る。
- **絵がちがう**（`kind: "wrong"`）… 引けたのに、出てきた絵が別物。
  → 絵そのもの（型の割り当て）を直すしかない。

実例：`フルーツグラノーラ` は辞書に当たります（`product-icons.js` の
`cereal`）。当たった先の `cereal` が 25px で崩れないよう
**「箱もの」型に寄せられていました**（`icons-food.js` の `bento`、
`icon-types.json` の `箱もの`）ので、弁当箱が出ていました。語彙の穴では
なく、**型の飲み込み**です。直しかたが根本から違うので、**分けずに溜め
ると、渡された側がもう一度分け直すことになります。**

**この一件は直しました**（`icons-food.js` の `MEMBERS.bento`）。
弁当箱の丸みは「盛り付け・出来合いの食事」を言う形で、箱入りの乾いた
穀物とは実物として別物——71型のどれにも箱そのものの形（角の立った
縦長の紙箱）が無く、参考画像も無いので、**似て非なる型へ畳み直すのは
見送りました**（新しい型を描くのは `ICON-DEIMAGINE.md` の手順どおり、
参考画像をなぞってから）。かわりに `cereal` を `bento` の仲間から外し、
無印の色つき丸（`fallback`）へ戻しました。**間違った絵より、絵が無い
ほうがよい**——この表がずっと守ってきた物差しのままです。`frozen`（同じ
`bento` の仲間だった）は、実物として弁当箱の丸みで合っているので、
そのまま残しています。

食材71型の総点検（他にも同じ「型の飲み込み」が無いか）は、まだ手を
付けていません。実測（Playwright で25px描画・画素数え）を要する重い
作業なので、必要になったときに改めて着手します。

**判定は画面の側が渡します**（`addIconReport` の `kind`）。引く順番
——やること＝こと辞書→品物辞書、買うもの＝品物辞書（カテゴリの当たりも
含む）——を知っているのは画面だけなので、store で引き直すと**画面に
出ている絵と違う答え**を出しかねません。渡されなければ `gotIcon` から
割り出します（絵が出ていた＝`wrong`、出ていなかった＝`missing`）。

`state.iconReports` は `{id, text, screen, gotIcon, kind, chosen, note,
createdAt}`。**古い報告は後ろの三つを持っていない**ので、
`cleanIconReport()` が読み込みのたびにいまの形へそろえます。あれは
`reconcile()` 経由＝**load の経路にいる**ので、`function` 宣言で置くこと
（`const` で下に書くと TDZ で落ちます）。

**報告は、この端末に溜まるだけです。** 外と話す口は中継所URLだけで、
それは資格情報なので触れません——だから「この絵はちがう」を送る先は
どこにもありません。見返す・またはコピーして次のセッションに渡すための
場所です。

- **入口は絵選び紙の腕組みボタン**（`.icon-report-toggle`）。押した瞬間に
  書かず、**次に `choose()` が呼ばれたとき**（格子の絵、または「おまかせに
  する」）に、その結果を `chosen` として一緒に書きます。押した時点では
  まだ何が正しいか分からない——分かっていれば選んでいる——ので。
  「おまかせ」のまま報告すれば `chosen` は空で、それが
  **「正しい絵はまだ無い」という記録そのもの**になります。
- **`gotIcon` に入れるのは、辞書の自動の推測です**（いま `product.icon` /
  `t.icon` に入っている値ではない）。手で選んだ絵を挟んだあとに報告しても、
  辞書がどちらの困りごとを起こしているかは変わらないので。
- **探す欄のすぐ下に置くこと。** 格子（「ぜんぶ」は700枚超）の**下**に
  置いていた時期があり、見つけてもらう前にスクロールで力尽きる位置
  でした。まず選ぶか、まず報告するかは同じ一手の距離にします。
- **同じ言葉・同じ画面の報告は差し替えます。** 知りたいのは「どの言葉が
  困っているか」で、同じ言葉が何件あるかではないので。新しいほうが
  `chosen` を持っている、という理由もあります。
- **入口はもう一つ、「合う絵はありません」の下にもあります**
  （`.js-report-empty`。「探す欄は、見出し名にも答える」の節）。腕組み
  ボタンは「選ぶかもしれない絵」に相乗りする形なので、探して**何も
  出なかった**ときは相乗りする相手がありません。そこだけは、いま打った
  言葉をその場で直接記録します——`chosen` を持たない、いちばん単純な形の
  報告です。
- 設定のページ（「アイコンについて」）は**見出しを二つに割ります**
  （`iconReportsGroup`）。上の「絵が見つからない言葉」（`collectIconGaps`）
  と混ぜないこと——あちらは辞書に一度も当たらなかった記録を**自動で・
  横断的に**拾うもの、こちらは**手で**残した個別の困りごとです。
  そして**「絵がちがう」は自動では拾えません**（辞書は当たっているので）。
  そこがこの仕組みの取り分です。
- **自由記述の追加欄は、どの画面のつもりかを知りません**（品目にも用事にも
  まだ結びついていない言葉を確かめる入口なので）。`screen: ""` で足し、
  こと辞書→品物辞書の順で引いて `kind` を自動で振り分けます。
  **`screen: "shop"` 決め打ちに戻さないこと**——やることの言葉を打った人が
  「買うもの」と記録されます。
- **中の一覧は、空でも同じ入れ物を保つこと**（`.js-rep-body`）。空の
  ときだけ要素ごと差し替える作りにしたら、次の repaint がもう外れた
  要素を触っていました——空/件ありは**中身**の出し入れで言うこと。
- コピーは JSON（`{kind, screen, text, gotIcon, chosen, note}` の配列）。
  タブ区切りの「絵が見つからない言葉」と違うのは、渡す先での使い道が
  違うからです——あちらは辞書に言葉を足す作業への入力、こちらは
  「この入力にはこの絵が出た、正しいのは何か」を考える作業への入力
  なので、`icon-eval.json` と同じ形に寄せてあります。
